# CLAUDE.md - Epoch Project Conventions

## Project Overview
Epoch is a distributed hyperparameter optimization system using a genetic algorithm.
A C++ job scheduler communicates with Python workers via gRPC. Workers train
TensorFlow/Keras CNN models. A Python GA layer drives the evolutionary search.

## Repository Layout
- `protos/` - Protobuf/gRPC service definitions (single source of truth for API)
- `scheduler/` - C++ job scheduler (CMake-based)
- `worker/` - Python TF/Keras training workers
- `ga/` - Python genetic algorithm engine
- `metrics/` - Python metrics collection and visualization
- `benchmarks/` - Benchmark comparison framework (GA vs random vs grid vs Bayesian)
- `generated/` - Generated protobuf code (gitignored, regenerated by build)
- `scripts/` - Build, run, and test scripts
- `results/` - Output directory for metrics and plots (gitignored)

## Build Instructions

### C++ Scheduler
```
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . --target epoch_scheduler -j$(nproc)
```

### Python Environment
```
poetry install
bash scripts/generate_protos.sh
```

### Run Tests
```
# C++ tests
cd build && ctest --output-on-failure
# Python tests
poetry run pytest
```

## Code Style

### C++
- Google C++ Style Guide (enforced by .clang-format)
- Header guards: `#pragma once`
- Namespace: `epoch`
- Class names: PascalCase (for example, `WorkerPool`, `JobQueue`)
- Methods: PascalCase (for example, `EnqueueBatch`, `GetIdleWorker`)
- Member variables: trailing underscore (for example, `mu_`, `workers_`)
- Use `std::mutex` + `std::condition_variable` for synchronization
- Use `std::unique_ptr` for ownership, raw pointers for non-owning refs
- C++17 standard

### Python
- Black formatter (line length 100)
- Ruff linter
- Type hints on all function signatures
- Docstrings on all public classes and methods (Google style)
- Imports: standard lib, third-party, local (enforced by ruff isort)
- Class names: PascalCase
- Functions/methods: snake_case
- Private members: leading underscore

### Protobuf
- proto3 syntax
- Package: `epoch`
- Enum values prefixed with enum name and start with UNSPECIFIED = 0
- Messages use PascalCase, fields use snake_case

## Key Architectural Decisions

### gRPC Communication Pattern
- `WorkerService.Connect`: Bidirectional streaming between scheduler and workers.
  Workers send registration, heartbeats, and results. Scheduler sends job
  assignments and shutdown commands. This avoids reconnection overhead.
- `SchedulerControl.*`: Unary RPCs for the GA controller (one call per generation).

### Threading Model (C++ Scheduler)
- gRPC server threads are managed by gRPC internals
- 1 dedicated dispatch thread matches pending jobs to idle workers
- 1 heartbeat monitor thread checks for worker timeouts every 5 seconds
- All shared state protected by per-component mutexes (no cross-lock dependencies)

### GA Design
- Elitism: top N individuals pass to next generation unchanged
- Adaptive mutation: rate decays from 0.3 to 0.05 over generations
- Default operators: ElitistSelection + UniformCrossover + AdaptiveMutation
- All operators are pluggable via strategy pattern (ABC base classes)

### Fitness Function
- Primary: validation accuracy on held-out test set
- Failed/timed-out configs receive fitness = 0.0

## Common Tasks

### Adding a new hyperparameter
1. Add field to `HyperparamConfig` in `protos/epoch.proto`
2. Regenerate protos: `bash scripts/generate_protos.sh` + rebuild C++
3. Add `ParamSpec` entry in `ga/search_space.py:SearchSpace.default_cnn_space()`
4. Map it in `ga/individual.py:Individual.to_protobuf()` and `from_protobuf()`
5. Use it in `worker/model_builder.py` or `worker/trainer.py`

### Adding a new GA operator
1. Create class in appropriate file under `ga/operators/`
2. Inherit from the ABC (`SelectionStrategy`, `CrossoverStrategy`, `MutationStrategy`)
3. Add unit tests in `ga/tests/`
4. Wire it into `GAConfig` defaults or pass explicitly

### Adding a new benchmark strategy
1. Create class in `benchmarks/strategies/` inheriting from `SearchStrategy`
2. Implement `name()` and `run()` methods
3. Add to strategy list in benchmark runner

## Environment Variables
- `EPOCH_SCHEDULER_ADDRESS` - Override scheduler address (default: localhost:50051)
- `EPOCH_WORKER_AUTH_KEY` - Shared auth key for worker registration (default: `superkey`)
- `TF_CPP_MIN_LOG_LEVEL=2` - Suppress TensorFlow info logs
- `CUDA_VISIBLE_DEVICES` - Control GPU visibility per worker

## Performance Notes
- Workers cache datasets in memory after first load.
- `tf.keras.backend.clear_session()` is intentionally NOT called after every job
  because it tears down TF runtime and hurts throughput.
- Workers free model references and run `gc.collect()` after each job.
- Scheduler dispatch interval default is 10ms (`--dispatch-interval` configurable).
- Worker heartbeat interval default is 10s.
- Scheduler heartbeat timeout default is 30000ms (`--heartbeat-timeout` configurable).
- XLA JIT is disabled in workers (`TF_XLA_FLAGS=--tf_xla_auto_jit=0`) because compile
  overhead dominates stress-test job runtime.
- Worker timeout is callback-based and effectively soft; jobs can exceed nominal timeout
  under heavy load before returning timeout results.
- `StatusCode.UNAVAILABLE` in workers during shutdown is expected when scheduler exits first.

## Running Epoch

### Main entry point: `run_ga.py`
The primary entry point for the GA optimization loop. Defaults to stress mode.
```
# Default: stress mode (small models)
python run_ga.py

# Full-scale optimization
python run_ga.py --mode full --pop-size 20 --generations 10 --epochs 10

# Save per-run throughput/status summary
python run_ga.py --summary-output results/my_run_summary.json
```
Requires the C++ scheduler to be running and workers connected.

### Full distributed run: `scripts/run_stress_test.sh`
Orchestrates the full stack: starts scheduler, spawns workers, runs GA.
```
bash scripts/run_stress_test.sh
```
Override via env vars:
- `NUM_WORKERS`, `GPU_MEMORY_MB`, `TRAIN_SUBSET`, `VAL_SUBSET`
- `WORKER_TIMEOUT`, `RUN_EAGERLY`
- `POP_SIZE`, `NUM_GENS`, `DATASET`
- `DISPATCH_INTERVAL_MS`, `HEARTBEAT_TIMEOUT_MS`
- `SCHEDULER_LISTEN_ADDRESS`, `SCHEDULER_PUBLIC_ADDRESS`
- `GA_SCHEDULER_ADDRESS` (defaults to `localhost:50051`; useful when workers use a public tunnel)
- `START_LOCAL_WORKERS` (set `0` when using remote workers like Modal)
- `WORKER_AUTH_KEY` / `EPOCH_WORKER_AUTH_KEY`
- `RESULTS_DIR`, `OUTPUT_NAME`

Outputs:
- `results/<name>.json` (generation metrics)
- `results/<name>_summary.json` (run summary including jobs/sec, avg_job_ms, timeouts, failures)

### Modal remote workers: `scripts/modal_workers.py`
Launches long-lived Modal GPU workers that connect back to the same C++ scheduler.
```
modal run scripts/modal_workers.py::launch \
  --scheduler-address <public-host>:50051 \
  --num-workers 8
```
If you need a quick public TCP endpoint for local scheduler dev runs, use:
```
powershell -ExecutionPolicy Bypass -File scripts/ngrok_scheduler_tunnel.ps1
```
This starts `ngrok tcp 50051` and prints the `host:port` value for `SCHEDULER_PUBLIC_ADDRESS`.

Key handling:
- Set `EPOCH_WORKER_AUTH_KEY` to your own key (recommended), or
- leave unset and it falls back to `superkey`.
- A starter template is provided at `scripts/modal.env.example`.

### Throughput tuning: `scripts/tune_throughput.sh`
Automated throughput-first tuning campaign:
- Runs C++ guard tests (`test_job_queue`, `test_worker_pool`)
- Runs smoke check + baseline x3
- Sweeps worker count, memory, eager mode, subset size, timeout, and dispatch interval
- Runs aggressive failure-mode check
- Runs medium validation + repeatability + long stress
- Selects best config under failure-rate threshold

Outputs:
- `results/throughput/throughput_runs.csv`
- `results/throughput/throughput_local_3070.env`
- `results/throughput/throughput_report.md`

### Search space modes
- `stress` (default): `SearchSpace.stress_test_cnn_space()` for higher throughput testing
- `full`: `SearchSpace.default_cnn_space()` for broader optimization

### Worker CLI args
- `--gpu-memory-limit <MB>` - VRAM per worker (default: 750)
- `--train-subset-size <N>` - Training sample cap (0 means full dataset)
- `--val-subset-size <N>` - Validation sample cap (0 means full test set)
- `--timeout <sec>` - Per-job timeout
- `--run-eagerly` - Optional eager mode (often slower for this workload)

- Throughput-first preflight example: 150 jobs in about 72.8s (~2.06 jobs/sec)
- End-to-end avg job wall-clock in that profile: ~485ms/job
- Workload is currently compute-bound in worker training (TF build/fit/eval), not scheduler-bound
- Aggressive configs can trigger timeout storms in later generations; use validated presets
